# qWDTT OpenWrt

[![Release](https://img.shields.io/github/v/release/romankuznetsov/qwdtt-openwrt)](https://github.com/romankuznetsov/qwdtt-openwrt/releases/latest)
[![Release date](https://img.shields.io/github/release-date/romankuznetsov/qwdtt-openwrt)](https://github.com/romankuznetsov/qwdtt-openwrt/releases/latest)
[![Downloads](https://img.shields.io/github/downloads/romankuznetsov/qwdtt-openwrt/total)](https://github.com/romankuznetsov/qwdtt-openwrt/releases)

RAW-IP клиент qWDTT для роутеров OpenWrt. Он поднимает интерфейс `qwdtt0` и
направляет через туннель IPv4-трафик устройств локальной сети. Сам роутер
сохраняет прямой доступ к WAN, поэтому соединения с VK TURN не зацикливаются.

Поддерживается только RAW-IP. WireGuard и SOCKS в этой сборке намеренно не
включены.

## История появления

Клиент qWDTT и сама идея принадлежат проекту
[SpaceNeuroX/qwdtt-openwrt](https://github.com/SpaceNeuroX/qwdtt-openwrt) -
без него этого репозитория бы не было.

Этот форк изначально создавался для личного пользования как дополнение к
исходному проекту. В какой-то момент форк был доработан, приведен в нормальный
вид и выложен для публичного использования - на случай, если кому-то окажется
полезным.

Также буду рад правкам, улучшениям и багфиксам.

## Отличия от исходного проекта

Этот проект добавляет графический интерфейс LuCI для настройки qWDTT-клиента
и упрощает его установку и обновление стандартными средствами управления
пакетами OpenWrt.

В исходном проекте клиент устанавливают вручную: скачивают tar.gz под свою
архитектуру и распаковывают. Здесь он собран пакетами OpenWrt и раздается
через feed.

- **Туннель - это интерфейс OpenWrt.** Network -> Interfaces, протокол qWDTT,
  с русским переводом. Его поднимает netifd, а не отдельный сервис, поэтому
  работают штатные кнопки Connect / Stop / Restart, зона в межсетевом экране и
  обычные `config route` и `config rule`. В исходном проекте настраивают по
  SSH, правкой файла.
- **Все настройки в UCI.** В исходном проекте `/etc/config/qwdtt` хранит
  только `enabled` и путь к `/etc/qwdtt/config.json`, который правят руками.
  Здесь каждая настройка - опция интерфейса в `/etc/config/network`, а
  обработчик протокола собирает из них аргументы запуска.
- **Стандартные пакеты OpenWrt** - `.ipk` на 24.10, `.apk` на 25.12. Работают
  штатные `opkg install` и `apk add`, зависимости подтягиваются сами.
- **Обновление вместо переустановки.** Настройки туннеля лежат в
  `/etc/config/network` рядом с остальными интерфейсами, поэтому установка
  новой версии их не трогает. Старый `/etc/config/qwdtt` переносится в
  интерфейсы автоматически при первом обновлении.
- **Подписанный feed.** Индекс подписан `usign` на 24.10 и ключом проекта на
  25.12. Роутер проверяет подпись при `update`, а каждый пакет - по хешам из
  индекса.
- **Сборка под 34 архитектуры пакетов**, в исходном проекте было только
  четыре самых распространенных. Тарболлы тоже остались: x86_64, aarch64,
  armv7, mipsel, mips.

Список будет дополняться.

## Состав пакетов

Два пакета. По отдельности они обычно не нужны: `install.sh` ставит все сам,
зависимости подтянет менеджер пакетов.

- `qwdtt-client` - клиент на Go и обработчик протокола для netifd. Клиент
  создает TUN-интерфейс, названный по интерфейсу, и получает у сервера адрес,
  DNS и MTU; netifd запускает клиент, следит за ним и владеет адресом и
  маршрутами. Один интерфейс - один туннель.
- `luci-proto-qwdtt` (не обязателен для работы) - протокол qWDTT в LuCI:
  вкладка qWDTT в редакторе интерфейса и страница Status -> qWDTT, где по
  одной строке на туннель: сервер, идентификатор устройства, число хешей,
  сколько воркеров работает из
  запрошенных, адрес и счетчики.
- `luci-i18n-qwdtt-ru` (не обязателен для работы) - пакет с русским переводом,
  подтягивается вместе с `luci-proto-qwdtt`.

## Что понадобится

- Роутер с OpenWrt 24.10 или 25.12.
- VPS-сервер qWDTT с включенным RAW-слушателем. Обычно это UDP-порт `56003`.
- Данные подключения: адрес сервера, пароль и хеш звонка VK.

## Установка

Два способа установить пакеты. Настройка после установки одинаковая - см.
раздел "Настройка".

### Способ 1: одной командой (SSH)

Подключитесь к роутеру по SSH по его IP-адресу, например 192.168.1.1:

```sh
ssh root@192.168.1.1
```

и выполните:

```sh
wget -qO- https://raw.githubusercontent.com/romankuznetsov/qwdtt-openwrt/main/install.sh | sh
```

Скрипт сам определяет менеджер пакетов, добавляет подписанный feed и его ключ
доверия, затем ставит `qwdtt-client`, `luci-proto-qwdtt` и зависимости.

### Способ 2: через LuCI (без SSH)

Полностью через веб-интерфейс. Порядок зависит от менеджера пакетов: `apk` на
OpenWrt 25.12, `opkg` на 24.10.

Подробно о feed, ключах, архитектурах и типовых ошибках -
[docs/custom-feed.md](docs/custom-feed.md).

#### OpenWrt 25.12 (apk)

Отдельные `.apk` не подписаны, поэтому доверие дает ключ feed, а не загрузка
файлов пакетов - загруженный через LuCI пакет ставится недоверенным.

1. Установите ключ доверия. Скачайте `qwdtt-apk-key.tar.gz` со страницы
   [Releases](../../releases/latest) и восстановите архив в
   System -> Backup / Flash Firmware -> "Restore". Он кладет публичный ключ в
   `/etc/apk/keys` - без него feed недоверенный.
2. Добавьте feed. В System -> Software -> Configuration допишите строку для
   своей архитектуры (полный список - на
   [странице feed](https://romankuznetsov.github.io/qwdtt-openwrt/)), например
   для `aarch64_cortex-a53`:

   ```
   https://romankuznetsov.github.io/qwdtt-openwrt/releases/25.12/aarch64_cortex-a53/packages.adb
   ```

   Сохраните, затем нажмите "Update lists…".
3. В System -> Software установите пакеты `qwdtt-client` и
   `luci-proto-qwdtt`.

#### OpenWrt 24.10 (opkg)

Порядок тот же, что и для 25.12, но feed и ключ - свои: opkg читает индекс
`Packages` и проверяет его подпись через `usign`.

1. Установите ключ доверия. Скачайте `qwdtt-opkg-key.tar.gz` со страницы
   [Releases](../../releases/latest) и восстановите архив в
   System -> Backup / Flash Firmware -> "Restore". Он кладет публичный ключ в
   `/etc/opkg/keys` под именем его key id.
2. Добавьте feed. В System -> Software -> Configuration допишите строку для
   своей архитектуры, например для `mipsel_24kc`:

   ```
   src/gz qwdtt https://romankuznetsov.github.io/qwdtt-openwrt/releases/24.10/mipsel_24kc
   ```

   Сохраните, затем нажмите "Update lists…".
3. В System -> Software установите пакеты `qwdtt-client` и
   `luci-proto-qwdtt`.

## Настройка

Туннель - это интерфейс в `/etc/config/network` с `option proto 'qwdtt'`. Его
поднимает netifd, а настраивают через LuCI (Network -> Interfaces) или командой
`uci`. Один интерфейс - один туннель, и они работают одновременно.

Имя интерфейса - это имя TUN-устройства. Отсюда ограничение в 15 символов и
смысл префикса: зона `qwdtt` в межсетевом экране принимает устройства по
шаблону `qwdtt+`, поэтому имя, которое начинается с `qwdtt`, попадает в нее
само, а имя с другим началом придется добавить в зону вручную.

Туннелю обязательно нужна своя таблица маршрутизации, `ip4table`. В основной
таблице маршрут по умолчанию через туннель увел бы в него и собственный трафик
клиента к серверам VK, и туннель не поднялся бы никогда. Без нее обработчик
протокола не запускается и пишет причину на странице интерфейса.

### Через LuCI

1. Network -> Interfaces -> "Add new interface...", протокол qWDTT, имя -
   например `qwdtt0`.
2. Заполните адрес сервера, порт, пароль и хеши звонка. Свободная таблица
   маршрутизации уже подставлена.
3. Обе галочки маршрутизации уже включены. "Направить локальную сеть в этот
   туннель" пишет обычное правило, отправляющее трафик локальной сети в таблицу
   этого туннеля; "Удерживать трафик, пока туннель не работает" - это kill
   switch, маршрут по умолчанию типа `unreachable` в той же таблице. Каждая
   галочка пишет свою секцию, поэтому одну можно выключить, не трогая другую.
   Обе секции потом можно править в разделе Network -> Routing: чтобы направить
   в туннель один компьютер или одно назначение вместо всей сети, сузьте там
   правило - таким оно и останется.
4. Save & Apply.

Пароль и хеш нельзя публиковать или отправлять посторонним.

### Через UCI

```sh
uci set network.qwdtt0=interface
uci set network.qwdtt0.proto='qwdtt'
uci set network.qwdtt0.ip4table='51820'
uci set network.qwdtt0.peer_host='IP_АДРЕС_СЕРВЕРА'
uci set network.qwdtt0.peer_port='56003'
uci set network.qwdtt0.device_id='ИДЕНТИФИКАТОР_УСТРОЙСТВА'
uci set network.qwdtt0.password='ПАРОЛЬ'
uci add_list network.qwdtt0.hash='ХЕШ_ЗВОНКА'

uci set network.qwdtt0_rule=rule
uci set network.qwdtt0_rule.in='lan'
uci set network.qwdtt0_rule.lookup='51820'
uci set network.qwdtt0_rule.priority='10000'

uci set network.qwdtt0_killswitch=route
uci set network.qwdtt0_killswitch.interface='loopback'
uci set network.qwdtt0_killswitch.target='0.0.0.0/0'
uci set network.qwdtt0_killswitch.type='unreachable'
uci set network.qwdtt0_killswitch.table='51820'
uci set network.qwdtt0_killswitch.metric='4096'

uci commit network
ifup qwdtt0
```

Второй туннель - это второй интерфейс со своей `ip4table` и своим правилом,
которое говорит, какой трафик он несет: по источнику (`option src`) или по
метке межсетевого экрана (`option mark`).

Остановить и запустить туннель можно кнопками Stop и Connect на странице
интерфейса или из шелла:

```sh
ifdown qwdtt0
ifup qwdtt0
```

Вернется ли туннель после перезагрузки, решает не это, а `option disabled` и
`option auto` - обычные настройки интерфейса.

## Что происходит, пока туннель переподключается

TUN-устройство живет дольше клиента: перезапуск его не удаляет. Поэтому
соединение, привязанное к интерфейсу (`curl --interface qwdtt0`,
`iperf3 --bind-dev qwdtt0`), переживает переподключение и продолжается само,
а не обрывается намертво: номер интерфейса не меняется, а записи conntrack
переживают перезапуск и подхватывают поток обратно.

Ради этого зона `qwdtt` не маскарадит и не отвечает REJECT. Маскарадинг
сбрасывал бы conntrack каждый раз, когда устройство уходит вниз, а REJECT
отвечал бы сбросом TCP на пакеты, которых conntrack уже не узнает, и убивал бы
соединения, которые всего лишь прервались. Вместо маскарадинга адрес, выданный
сервером, подставляется правилом SNAT, которое пишет `/lib/netifd/qwdtt-up.sh`.

Пока туннель лежит, трафик, направленный в него, отбрасывается, а не уходит
напрямую через WAN. Это kill switch: в таблице туннеля лежит маршрут по
умолчанию типа `unreachable` с большой метрикой, и он остается единственным,
когда маршрут самого туннеля исчезает. Лучше остаться без интернета, чем
выпустить трафик мимо туннеля.

Устройство убирается только тогда, когда интерфейс перестает быть туннелем
qWDTT - когда секцию удаляют или меняют ей протокол. `ifdown` его оставляет,
чтобы следующий `ifup` подхватил тот же номер интерфейса.

## Проверка

Состояние туннеля и счетчики - на странице Status -> qWDTT. Журнал она не
показывает: он и так есть в System -> System Log, а из шелла короче. Оттуда
же:

```sh
ubus call network.interface.qwdtt0 status
logread -e qwdtt0
```

netifd подставляет в начало каждой строки имя интерфейса, от которого она
пришла, поэтому `logread -e qwdtt` показывает все туннели сразу, а
`logread -e qwdtt0` - только один. Рабочее подключение пишет
`RAW config received`, затем `TUN attached, traffic is flowing`.

Маршруты и правила:

```sh
ip addr show qwdtt0
ip rule show
ip route show table 51820
```

В таблице туннеля должно быть два маршрута по умолчанию: через `qwdtt0` и
`unreachable` с метрикой 4096. Если остался только второй, туннель лежит и
kill switch работает.

Если туннель не поднимается, причина написана на самой странице интерфейса:
`No server address is set`, `The connection password belongs to another device
ID` и так далее. После исправления настроек нажмите Connect - Save & Apply
сам по себе туннель не перезапустит.

Проверка создания TUN без данных VK и сервера:

```sh
/usr/bin/qwdtt-client -rawtun-self-test 10.70.0.2
```
